# Infinite Alchemy v2 — Architecture

Infinite Alchemy (est. May 2023) is an AI-powered element-combining game: drag two or
more elements together and an LLM decides what you made; an image model paints it.
v2 is a ground-up rewrite. This document is the source of truth for how it fits together.

## Stack

| Layer | Choice | Why |
|---|---|---|
| Frontend | Vite 8 + React 19 SPA, TypeScript, Tailwind CSS v4, `motion` (pinned), `@tanstack/react-virtual`, `radix-ui` (Dialog/Popover only), `zustand`, `qrcode.react` (transfer QR; lazy Settings chunk only) | The game is one interactive screen; a static SPA costs zero function invocations to serve. |
| Backend | Netlify Functions v2 (`netlify/functions/*.mts`, web-standard `Request`/`Response`, path routing, `config.rateLimit`) | Small per-endpoint bundles, fast cold starts, and native platform rate limiting (Next.js route handlers can't declare Netlify rate limits and run as one large function). |
| DB | Existing CockroachDB Cloud (Basic, us-east1) via `pg` + raw SQL | New tables live in SQL schema `alchemy` next to the untouched legacy `public."Alchemy*"` tables. |
| Image storage | Netlify Blobs store `element-art`, served by `/img/:id/:key.webp` with immutable CDN caching; resized through Netlify Image CDN | No native deps; one function call per image per CDN, then free. |
| LLM | OpenAI `gpt-6-luna`, Responses API, strict JSON schema, `reasoning.effort: "none"`, temperature 0, prompt in `server/ai/prompts.ts` | ~1.5 s, ~$0.0001 per new recipe. |
| Images | OpenAI `gpt-image-2.5-flare-2026-09-08`, 816×816, `quality: "low"`, transparent webp | ~$0.005 and ~8 s per image; generated lazily on first need. |
| Sort AI | TypeSafe Jev `jev-1.14.0` (System One `score`/`choice`/`noul` questions), raw `fetch` in `server/ai/jev.ts` | ~$0.004 per 1k-element rank sort (measured 92 input tokens per element for rank, ~153 for 3 groups, ~256 for 8 groups ≈ $0.011 per 1k; output is free); numbers only, never text. |

Hosting constraints that shape the design (Netlify legacy **Starter** plan, $0, plus the
**Functions Level 1** add-on, $25/site/month, which Netlify applies automatically whenever a site
passes Level 0's 125k calls or 100 hours; this site always does): 2M function calls and 1,000
function-hours per site/month, 100 GB bandwidth, **2 platform rate-limit rules**. Usage
(2026-11): ~250-330k calls and ~15-20 GB-hours a month, so OpenAI spend, not Netlify, is the
binding cost. Do not move to a credit-based plan: deploys (15 credits each), compute and requests
all draw credits, and a plan out of credits suspends the site. So: static pages, one bootstrap call per
session, client-side recipe cache, CDN-cached images, and rate limits in front of the costly paths.

## Data model

See `db/migrations/0001_init.sql`. Key rules:

- **Elements** are unique by `name_key` (see `src/shared/names.ts`). `name` is display text
  (title-cased for legacy rows; LLM casing for new rows, e.g. "Isaac Newton"). `fold_key`
  lets a new LLM answer like "time-travel" reuse an existing "time travel".
- `status = 'quarantined'` elements (legacy spam) are kept so every legacy id still maps,
  but they are never shown, never combinable, and never challenge targets.
  `quarantine_reason` says why: `legacy-filter` (backfill), `review` (purged junk) or
  `orphaned` (cut off by a purge; see "Element purge").
- **Recipes** are keyed by `ingredient_ids` = the ingredient multiset sorted ascending
  **numerically** (BigInt compare; duplicates kept). Once active, a recipe's result never
  changes — this guarantees daily challenges stay solvable. A recipe whose stored result is
  quarantined (and that is not `protected`) is "healed": the next combine re-rolls it with the
  LLM and updates the row.
- `depth` = generations from the starters (min over recipes of 1 + max ingredient depth);
  `steps` = min number of combinations (min over recipes of 1 + Σ steps of distinct
  ingredients). Both are only ever lowered; new recipes update them incrementally.
  Combine lowers only the result's row, so descendants drift high: run `npm run db:depth`
  (`scripts/recompute-depth.ts`, dry run unless `--run`; lowers only, never while `db:purge`
  apply/restore runs) periodically. Increases (after a purge) belong to `db:purge`.
  Rarity is derived from depth at read time (`src/shared/rarity.ts`).
- **Discoveries** = a player's library (`player_id, element_id`). Starters are inserted on
  player creation.
- **Challenges**: one row per day with easy/hard/expert targets. Days before
  `CHALLENGE_CUTOVER_DAY` (2026-11-06) are legacy history; days from the cutover for 5 years
  are produced by `scripts/generate-challenges.ts`.
- **Recognizable targets**: `elements.recognizable` (set by `npm run db:classify` with gpt-6-luna, run before `db:challenges`) marks real, widely known names; each generated tier draws only recognizable candidates ("Geyser", not "Temporaplasm"), falling back to all eligible ones, recognizable first, if fewer than 40 exist.
- **Counters** power rate limits, global daily budgets and PoW replay protection
  (single-statement UPSERT increments; row-level TTL cleans up).
- **Element reports** (`element_reports`, migration 0009): one row per (player, element) from
  "Report this element", first report wins (`reason`: inappropriate | wrong | other | NULL). Read
  only in aggregate, as input to the purge review; a report changes nothing in the game.
- **Player signals** (migration 0009): `players.acq_touch`, `acq_wide`, `acq_prior_local`,
  `standalone_at` and the `player_days` timing columns. See "Analytics".

All ids are INT8 and travel as decimal strings (they exceed JS safe integers).
`pg` type parsers: INT8 → string (default), DATE (1082) → string, TIMESTAMP (1114) → treat as UTC.

## Game rules

- Starters: Earth, Water, Air, Fire, Time. Shelf order is `STARTER_ORDER` in
  `src/shared/starters.ts` (Water, Fire, Earth, Air, Time): its first two are the onboarding demo
  pair (`DEMO_RECIPE`, used by the How-to-play demo and copy), and the library's time and rarity
  sorts break the starters' tie with it.
- Combine 2–4 owned elements (duplicates allowed). Order never matters.
- Known recipe → result immediately. Unknown → LLM proposes `{name, emoji, description, notable}`;
  the server validates with `checkName` (retry once with feedback, then `fizzled`, nothing saved).
  The LLM must never return an ingredient unchanged.
- `ruleViolations` (`server/ai/common.ts`) also rejects the old model's naming ladders that the
  purge removed, each with retry feedback: counted/multiplied forms (Double/Quadruple Flag,
  Doublejar, Twin X, X Trio, Pair of X, N-fold), spelled-out sums (Sixty-Four), hype prefixes
  spaced or glued (Mega Mountain, Megageyser) and meme suffixes (Cakeception, Smogzilla), plus
  ingredients glued with a shared letter (Dreamachine). An allowlist keeps established terms
  (Double Rainbow, Twins, Supernova, Steampunk, Tornado); proper nouns skip all but the
  multiplier check. Prompt rule 8 asks for the same up front.
- The first player to create an element is its discoverer ("First discovery").
- Daily challenge: producing a target via any combine on that day completes the tier.
  Tiers from the legacy generator: easy = BFS tier 2, hard = tier 4, expert = tier 6
  (BFS over active 2-ingredient recipes from the starters).
- Reset progress: library back to starters; firsts and challenge history are kept.
- Free. No credits, no payments.

## API (contract: `src/shared/api.ts`)

| Endpoint | Function | Notes |
|---|---|---|
| `POST /api/bootstrap` | `bootstrap.mts` | Session + library + stats + today's challenge + history + recent + `tomorrow` (teaser). Creates the player (PoW-gated) or adopts a legacy player. One call per page load (plus one automatic retry, and a silent refresh when a tab resumes on a new day: `refresh: true`, counted as no load; see "Boot"). Optional `hint` (client signals, see "Analytics"). |
| `POST /api/combine` | `combine.mts` | Platform rate rule #1. Ownership-checked. |
| `POST /api/image` | `image.mts` | Platform rate rule #2. Lazily generates art (sync, ≤ ~25 s) under a DB lease. |
| `GET /img/:id/:key.webp` | `img.mts` | Serves Blobs bytes with `Cache-Control: public, max-age=31536000, immutable` and `Netlify-CDN-Cache-Control: public, durable, max-age=31536000, immutable`. |
| `POST /api/player` | `player.mts` | `reset`, `transfer-code`, `redeem`. |
| `POST /api/sort` | `sort.mts` | No platform rule (both are used). Ownership-checked; names from the DB; app limits + `JEV_DAILY_CAP`. Combine piggybacks `sortScore` for a new discovery. See "Custom sort". |
| `POST /api/report` | `report.mts` | `{id, reason?}` → `{ok: true}`. "Report this element" (details menu). Session required; only elements the player owns or a target of a challenge that is "today" somewhere; `report.player` 20/day; `INSERT … ON CONFLICT DO NOTHING` into `element_reports`. |
| `POST /api/beacon` | `beacon.mts` | `{phase, ms, resumed?}` as **text/plain** (navigator.sendBeacon can't set the API header): a page hidden or left before the game was playable, or (`resumed: true`, same phase and ms) that page coming back, which takes the abandon back. Same-origin by `Sec-Fetch-Site: same-origin` or a matching `Origin`, 512 B cap, `beacon.ip` 120/h, phase from `BOOT_PHASES`. Only bumps the daily stat `boot_abandon:<phase>:<band>:<ua class>` (or `boot_resumed:…`); answers 204. |

Every POST requires `content-type: application/json` and header `x-ia-client: 1`, a body
under the per-route size cap, and (when present) a same-origin `Origin`/`Sec-Fetch-Site`.
The one exception is `/api/beacon` (above), which stores nothing but an aggregate count.
Errors use `ApiError` with the right HTTP status (400/401/403/404/429/503/422).

`tomorrow` (`TomorrowTeaser`) is tomorrow's easy target, for the player's local day + 1: `img`
only when its art is ready, and `letters` = its name's length without spaces; never its name or
id. It comes from the same element query as today's targets (`dailyChallenges`), so it costs no
round trip. New request fields are optional and new response fields optional on the client, so
an old client and a new server (or the reverse) keep working during a deploy.

### Boot (`bootGame`, `src/app/state/game.ts`)

- One run at a time (React StrictMode mounts twice). A failed attempt with code `network`,
  `timeout` or `server_error` (never a 4xx, `rate_limited` or `pow_required`) gets **one
  automatic retry** after a jittered 1.5-3 s, unless `navigator.onLine === false`; the boot pill
  stays up meanwhile. A new player whose second POST failed solves a new PoW on the retry.
- `bootstrap()` (`src/app/lib/api.ts`) records the attempt's phase (`bootstrap1` → `pow` →
  `bootstrap2` → `render`) and its PoW and API time (`BootTrace`) for `app_ready`/`load_failed`.
- On `pagehide`, or `visibilitychange` to hidden, before the game is ready, the client sends the
  abandon beacon (phase `wait` during the retry pause, `error` on the error screen) and, once per
  page, the GA `boot_abandon` event. Hidden and then closed is one abandon. A page that becomes
  visible again (or is restored from the back/forward cache) takes it back with a `resumed`
  beacon carrying the same phase and ms, whether or not the boot finished meanwhile, and a later
  exit sends a new abandon: pages lost before ready = `boot_abandon` − `boot_resumed`, per key.
- When a ready tab becomes visible on a new local day, `refreshIfNewDay` posts a fresh bootstrap
  (no PoW, no legacy, no hint, so it can never create a player) and swaps in the new challenge,
  stats, history, teaser and feed with no overlay. It sends `refresh: true`: the server moves
  `last_seen_at` but counts no load (no `player_days` row), so a tab that is merely shown again
  is not a return day; the day counts from the next combine or reload. Without a session it is
  refused (401 `unauthorized`), never a PoW challenge. Any failure keeps what is on screen (the
  next combine still offers a reload).
- The error screen's network copy points school networks at `/teachers`.

## Content pages and search (`src/shared/pages.ts`)

- **`PUBLIC_PAGES`** = `/`, `/how-to-play`, `/recipes`, `/daily`, `/about`, `/teachers`,
  `/privacy`: the one list of public, indexable URLs. The sitemap lists them, the deploy hook
  pings IndexNow for the ones that changed, and the `head-meta` e2e checks each one (own
  canonical, unique title/description, no cookie). A new page goes into this list.
- **Static pages.** `scripts/build-pages.ts` (`npx tsx scripts/build-pages.ts`; reads the DB only,
  never generates art or recipes; commit the output) writes `public/how-to-play.html`,
  `about.html`, `recipes.html` (real persisted recipes with existing art), `teachers.html`,
  `privacy.html`, `404.html` and `sitemap.xml`. Every page uses `renderPage` (one head with the
  first-touch `ia:acq` script, header and footer), works without JavaScript and never touches a
  session. Sitemap `<lastmod>`: a page keeps its date while its HTML is unchanged, else the build
  date; `/` uses `index.html`'s last commit; `/daily` has none (it changes every UTC midnight).
  `/teachers.html` and `/privacy.html` 301 to the clean paths; there is no catch-all, so anything
  else is a real 404.
- **`/daily`** (`daily.mts`, `GET`): today's three targets by UTC day, existing art only, CDN-cached
  until the next UTC midnight; never reveals another day.
- **`/teachers`** (wave 1): the classroom guide. Its QR code and Google Classroom button share
  `CLASSROOM_URL` (`/?utm_source=classroom&utm_medium=teacher`; `classroomShareUrl` is a plain
  link, so no Google script runs on the page), so classroom-link players land in
  `players.acq_utm_*`. It covers school networks and filters and points at "Report this element".
- **`/privacy`** (wave 1) lists everything the game stores. **Update it with every new stored
  signal** (wave 2 added the `player_days` timing and entry, `acq_prior_local`, the anonymous
  boot and PoW stats, and the new localStorage notes).
- **IndexNow** (Bing and the engines that share its submissions; key file `public/<INDEXNOW_KEY>.txt`).
  `deploy-succeeded.mts` runs after every production deploy: it hashes each `PUBLIC_PAGES` page
  (hashed asset names ignored), compares with `hashes` in the `indexnow` blob store and submits
  only the changed ones. A non-2xx answer keeps the old hashes, so the next deploy retries.
  `indexnow-daily.mts` is a scheduled function (`5 0 * * *`, just after `/daily` switches day) that
  pings `/daily` only, in production only; re-pinging unchanged pages would look like spam. Every
  submission is logged as `{time, urls, status, trigger}` under `log/<time>` in the same store.

## Sessions & identity

- Cookie `ia_session` = `base64url(JSON{p: playerId, v: sessionVersion, t: issuedAt}).hmacSha256`
  with `SESSION_SECRET`. `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=34560000` (400 days,
  refreshed on every bootstrap).
- No cookie → bootstrap answers `401 pow_required` with a signed PoW challenge
  (`salt = ts.rand.hmac`, ~18 bits). The client solves it in a Web Worker and retries.
  Salts are single-use (counters) and expire after 10 minutes.
- **Legacy players**: the old app stored `localStorage['alchemy:userId'] = {"value":"alchemy:<uuid>"}`
  and the discovered list in `localStorage['elements']` (array of legacy element objects).
  The backfill pre-creates a player for every valid legacy user id. On first visit the client
  sends `legacy` in bootstrap; the server adopts that player (sets the cookie), then imports
  the element ids (mapped via `legacy_element_map`, capped at 20k, max 3 imports per player).
  Only a request whose legacy user id belongs to a backfilled player imports; without one (or
  with an unknown one) nothing is written and the response says `imported: 0`, so a fresh
  player cannot fill its library with caller-chosen elements.
  The client remembers `ia:legacyImported` and never deletes the legacy keys.
- **Adopt-once** (migration 0005): legacy user ids are not secret (the 2023 API returned every
  element's creator id), so a legacy player is adopted by the first browser only. With a user id
  the client sends `legacy.claim`, a random 32-hex token it keeps in `ia:legacyClaim` and writes
  *before* the request; the server stores `sha256(claim)` in `players.legacy_claim_hash` and sets
  `legacy_claimed_at` in one atomic UPDATE (`claimLegacyPlayer`). Only a request carrying the same
  token adopts that player again (a lost response, or the same browser after its cookie was
  cleared). A player that is already claimed, or already played v2 (`last_seen_at`), is never
  adopted by anyone else: that browser falls through to normal PoW player creation and only gets
  a copy of the inventory (no firsts, no challenge history); the response says
  `legacyImport.claimed`, and the app shows a notice pointing at transfer codes from the bound
  device. `adopt.ip` (10/h) only slows mass claiming.
- Imported rows are dated when the element was made (for a legacy player: no earlier than the
  player's `created_at`), starters added on adoption at `created_at`, never `now()`. Elements a
  purge quarantined (`review`) or cut off (`orphaned`) are imported too, hidden like every
  non-active element, so a purge restore or a revival brings them back; `legacy-filter` spam is
  skipped. `imported`/`skipped` count active elements only.
- Transfer codes = signed `{p, v}`; redeem switches this browser to that player.
  Bumping `session_version` revokes all cookies/codes for a player.
  Settings also shows the code as a QR deep link `/#transfer=<code>` (`src/app/lib/transferLink.ts`):
  a fragment, so the bearer code never reaches the server, logs or referrers. On startup `main.tsx`
  strips it from the URL (`history.replaceState`) before anything else runs; after bootstrap (onboarding
  suppressed on that load) a confirm dialog redeems it and reloads. Malformed codes get the invalid-code
  toast without a request; your own code gets "You're already playing as this player" (compared by
  issuing a fresh code, since bootstrap only exposes the public id).

## Abuse & cost defenses

1. Netlify platform rate limits (per IP): `/api/combine` and `/api/image` — rejected
   requests never invoke a function. `/api/sort` has no platform rule (the Starter plan's two
   are used), so its app limits below are the only gate.
2. App-level fixed-window limits (counters; the table is in `server/ratelimit.ts`): per player
   and per IP for bootstrap, player creation, combine, new recipes (LLM), images, reset,
   transfer, sort (requests, plus items counted in Jev questions), reports and boot beacons. A request over a limit
   keeps its charge only on the rule it broke and the other counters are refunded, so a
   1-minute throttle never turns into an hour or day lock. 429 and 503 bodies name the rule
   (`limit`, e.g. `llm.player`); the client reports a 429 without a JSON body (the platform
   rule) as `platform`.
3. Global budgets: `JEV_DAILY_CAP` (default 2,500,000 Jev questions/day ≈ $10-13; when it runs
   out only custom sort stops, everything else keeps working), `LLM_DAILY_CAP` (default 100,000 new recipes/day ≈ $10),
   `IMAGE_DAILY_CAP` (default 2,000 images/day ≈ $10.60, ~1.5× the monthly average so no single
   week can spend the month), and `IMAGE_MONTHLY_CAP` (default 40,000 generations per 30 days
   ≈ $212, sized to ~1,100-1,400/day). The two image budgets are **paced** through their
   windows (see "Images"). Over budget → combine of *known*
   recipes still works; new recipes return `budget_exhausted`; images return `deferred`.
   Budgets are charged only after the per-player/per-IP limits pass (and, for new players,
   after the PoW salt is spent), and a budget denial refunds every counter of that request
   (budgets and per-player/per-IP alike), so rejected requests never consume them and a
   daily-cap denial no longer charges the monthly budget. Budget rows are kept 90 days past
   their window, as spending history.
   Daily stats (counters `stat:<name>:<UTC day index>`, kept 90 days, `bumpStat`):
   `denied:<rule>` for every limit or budget denial, `fizzle:<reason>` (`fizzleKind` in
   `server/game/combine.ts`), `art:<lane>:started` / `art:<lane>:deferred_<reason>`, the PoW
   funnel (`pow:issued:<browser|bot>`, `pow:redeemed:<browser|bot>`, `pow:latency:<band>` =
   issue-to-redemption time read from the salt) and `boot_abandon:<phase>:<band>:<ua class>`
   (the beacon), with `boot_resumed:<phase>:<band>:<ua class>` taking back the pages that came
   back. Bands (`LATENCY_BANDS`, `src/shared/api.ts`; GA `boot_band` uses the same): `<2s`,
   `2-4s`, `4-8s`, `8-15s`, `15-30s`, `30s+`. The issue count finishes after the 401 is sent
   (`context.waitUntil`) and the redemption stats run in parallel with the player-budget charge,
   so neither adds a round trip.
4. PoW on player creation; per-IP creation limits; global daily player cap.
5. Ingredient ownership is enforced, so automation must play legitimately to reach new recipes.
   Custom sort scores only the player's own active elements, with names read from the DB (the
   client sends ids), so it can't be used as a free scoring proxy.
6. Images are only generated for elements the player owns or today's challenge targets,
   for tiles actually on screen, with per-player hourly/daily caps (and a smaller daily cap on
   backlog art).
7. Input validation with zod; strict body-size caps; LLM output re-validated; ingredient
   names are passed as JSON-quoted data, never as instructions. Custom-sort prompts and group
   labels are cleaned (control/format characters, length) and passed to Jev only as JSON data
   fields; Jev answers with numbers, never text.
8. `AI_MODE=mock` is refused when `CONTEXT=production`.

## Images

`/api/image {id}`: if ready → path. Else, if eligible and within budget, claim a lease
(`UPDATE … SET image_status='pending', image_lease_until=now()+'45s', image_attempts=image_attempts+1
WHERE id=$1 AND (image_status IN ('none','failed') OR (image_status='pending' AND image_lease_until<now())) AND image_attempts<3`).
The winner calls the image model, stores `el/<id>/<key>.webp` in Blobs, and marks `ready`.
Others get `pending` with a retry hint. `moderation_blocked` → one retry without the name (the
element's hint, or for hint-less legacy rows a generic "a stylized <name>, the everyday thing …"
phrase); a second refusal → `blocked` permanently.
The client shows the procedural placeholder (emoji on a name-hashed gradient) until art is ready, then
fades it in. Tiles use `/.netlify/images?url=<img>&w=192&h=192&fit=contain` and fall back to the raw path.

**Lanes and pacing** (`server/game/images.ts`; `imageBudgets` in `server/ratelimit.ts`). Before
the lease, a request is put in a lane: **fresh** if this player discovered the element in the last
20 minutes (`discoveries.discovered_at`, so a client can't jump the queue) or it is a challenge
target that is "today" somewhere; **backlog** otherwise. Both lanes charge the same
`budget.image` (UTC day) and `budget.image.month` (30-day epoch window) counters, each against
an allowance that grows through its window:

- daily: `IMAGE_DAILY_CAP × min(1, CDF(t) + lead)`, CDF = the cumulative weekday share of
  world-first discoveries by UTC hour (GA 2026-11-16..20: 28% by 12:00, 91% by 21:00), linear
  within the hour; lead +0.10 for fresh, −0.05 for backlog;
- monthly: `IMAGE_MONTHLY_CAP × min(1, (elapsed + lead) / 30 days)`, linear accrual (~1,333/day
  at 40,000); lead 1 day for fresh, 0 for backlog.

So fresh art may run a little ahead of pace and backlog art only spends while spending is behind
it: the day's art lasts into US school hours (an unpaced 2,000 ran out around 12:00 UTC on
weekdays) and the month's lasts the month. Per player: `image.player.hour` 30 and
`image.player.day` 60 (generations started), plus `image.backlog.player.day` 20 on backlog art;
per IP: `image.ip.hour` 300 and `image.ip.day` 1,500. Any denial gives the lease and the attempt
back and answers `{state: "deferred", retryAfterMs, limited: true, lane, reason}` (`pace` |
`budget` | `player` | `ip`); for a pace denial `retryAfterMs` is the time until the allowance
reaches the count (at least a minute), otherwise the window end, capped at 15 minutes in the
backlog lane (clients from before the lanes paused their whole art queue for that hint). A failed
generation that can be retried answers `{state: "pending", retryAfterMs, failed: true}`.

The client (`src/app/lib/images.ts`) never waits out a window. A deferred element keeps its emoji
and rests: backlog art is asked for again only when a tile showing it next comes into view after
max(`retryAfterMs`, 10 min), or on the next page load, never from a timer. An over-pace budget
then costs one request per tile view, the art it can't pay for today is spread over the
following hours and days, and players who scroll through thousands of tiles meet a soft, visual
limit instead of an error. After any limited deferral, backlog requests wait `retryAfterMs`
clamped to 2-15 minutes, so a library scroll can't fire a burst of doomed requests. Fresh art
(discoveries of the last 20 minutes, from `noteFresh` or the library's `discoveredAt`, so a
reload keeps them fresh; today's targets) goes to the front of the queue,
skips the backlog hold and the session cap (150 backlog requests that could have started a
generation, including retries after a `failed` one; polls of a held lease and deferrals don't
count), and is retried on a timer after
max(`retryAfterMs`, 2 min) while on screen, up to 3 deferrals, then rests like backlog. An HTTP
429 pauses the whole queue for at least 10 s; 300 deferred replies end art requests for the
session. A share card asks for missing art with fresh priority and waits up to 10 s (3 s when
the share sheet will open, since `navigator.share` needs the tap's transient activation, which
lasts about 5 s) before drawing the placeholder, and draws it at once when the art can't come in
time: a deferral, a settled element or a queue pause ends the wait, and after a `budget`,
`player`, `ip` or given-up deferral it does not ask again until that hint has passed.

`elements.image_ready_at` (migration `0008_art_limits.sql`) stamps when art became ready, so art
latency is `image_ready_at − created_at` (world-firsts) or `− discoveries.discovered_at`.
**Apply migration 0008 before deploying the code that writes it** (the endpoint falls back to
an update without the column, so a late migration loses timestamps, never art).

Changing a cap mid-window moves its whole allowance line at once: raising `IMAGE_MONTHLY_CAP`
lifts the accrual line (and frees art) immediately; lowering it can leave spending above the new
line, which defers art until the accrual catches up. `IMAGE_MONTHLY_CAP=55000` is a **temporary**
Netlify override for the window that ends 2026-12-03 00:00 UTC: by 11-22 the default 40,000 was
~86% spent (34.4k, partly on charges the old limiter made on daily-cap denials), which is ~6 days
ahead of a 40,000 accrual line, so pacing without the override would defer nearly all art until
~11-28. Set it before (or with) the pacing deploy, and remove it, or choose the permanent budget,
when that window ends; otherwise the next window accrues at 55,000 too.

## Legacy migration (idempotent)

`npm run db:migrate && npm run db:backfill && npm run db:challenges && npm run db:enrich`

- Reads legacy tables read-only (`AS OF SYSTEM TIME follower_read_timestamp()`), keyset-paged.
- Elements: apply `checkName` (+ protection for challenge targets and their shortest paths)
  → active or quarantined; whitespace twins alias to the active row, which takes its date and
  first-discovery credit from the group's earliest spelling (an anonymous earliest spelling: no
  credit). Every legacy id lands in `legacy_element_map`. Legacy image URLs are ignored (all art
  is regenerated lazily).
- Recipes: ingredient list parsed from the legacy recipe `name` (authoritative, multiset),
  mapped through the element map, re-sorted numerically. Collisions: protected first, then
  oldest legacy id. Recipes referencing purged elements are dropped.
- Players: one per valid legacy user id (`^alchemy:<uuid v4 shape>$`), `legacy_user_id` set,
  `created_at` = the earlier of their credits row and their first element (only ever lowered on a
  re-run). Starters + elements they discovered first are seeded into their library.
- `npm run db:repair-legacy` (`scripts/repair-legacy.ts`; dry run unless `--run`) brings rows
  written before those fixes to the same state (player and twin dates, twin credit where it still
  equals what the backfill wrote, starter/import dates, one image retry); a re-run is a no-op.
- Challenge completions: OR-merged per (user, day), only rows with a completion.
- Challenges: legacy days before the cutover copied as-is.
- Emails, credits, and visit-only rows are not migrated.

## Element purge (`npm run db:purge`, `scripts/purge-elements.ts`)

Soft delete of junk names the 2023-2025 model produced ("Doublepanoramajungle"), decided by
two review passes of small models and never by the script itself:

1. `export --out <dir>` writes `batch-NNN.jsonl` (`{id, name, depth, made_from}`, every active
   non-starter outside the never-purge set) and `manifest.json`.
2. Reviewers run `stage --pass review --batch <n> --file <verdicts.json> --manifest <dir>/manifest.json`
   (`[{"id":"…","verdict":"purge"|"keep","reason":"…"}]`, all-or-nothing, idempotent) into
   `purge_review`; a second `verify` pass (`export --pass verify`) re-judges the review's purges.
3. `plan` (read-only) = review purge AND verify purge, minus the never-purge set (starters, every
   challenge target, the shortest derivations of the targets of every day that is "today"
   somewhere and of tomorrow's teaser day, protected recipes' elements), plus the cascade: active elements that were reachable
   from the starters and are not any more become `orphaned` (already-unreachable ones are left
   alone; never-purge ones are kept and reported). `--no-cascade` keeps those survivors active but
   unreachable instead (used for the first production run: most "orphans" were real names that
   only junk happened to lead to). Recipes whose result is removed are quarantined
   unless protected (the next combine heals them); recipes using a removed element are quarantined.
4. `apply --plan` re-validates, quarantines in batched transactions (run id `purge-YYYYMMDD-HHMMSS`
   in `elements/recipes.purge_run`, summary in meta `purge:<id>`), recomputes depth/steps, and
   re-picks generated days after tomorrow's teaser day (`liveWindow().frozenThrough` 2 h ahead;
   that day's easy target is already shown) whose targets the purge made inactive or moved out of
   their tier pool (the generator's pools: recognizable, school-safe, art not blocked, easy paths
   rule, steps order). `restore --run <id>` reverses a run (re-picked days stay).

Combine reactivates an `orphaned` element when the model names it again; any other quarantined
name still fizzles.

## Custom sort ("Sort by anything")

The library can be ordered by the player's own words: **rank** (`{kind: "rank", prompt}`,
e.g. "spookiest") or **groups** (`{kind: "groups", groups}`, 2–8 labels plus an implicit Other).

- **Server.** `POST /api/sort {spec, ids?}` (`server/game/sort.ts`) charges the request limits
  (alongside the session lookup) and only then loads the player's owned, active elements (all of
  them, newest first, capped at `SORT_MAX_ELEMENTS` = 25,000; or just `ids`, unowned ones dropped
  silently): the whole-library read scans every discovery, and `/api/sort` has no platform rule,
  so a rejected request must not start it. It then charges the item limits and `BUDGETS.jev` by
  cost = elements × questions (rank 1, groups 2), and scores them in one response.
- **Questions** (`server/ai/jev.ts`, rubric `SORT_RUBRIC` = `r2`). Rank: one `score` question per
  element over 5 generic levels, in requests whose `state` names the player's goal and says to
  read each name as the real thing it names (without it, "oldest" put Earth and Fire first and
  "heaviest"/"smallest" ranked by association). Groups: a `choice` over the groups (options
  rotated per element against first-option bias) plus a last, never-rotated "None of these
  groups" option, and a companion `noul` ("clearly belongs in one of these groups?"). When Jev
  picks None (about 45% of elements) `g` is the most likely real group; the fit is
  `n = noul × (1 − P(None))`, so weak fits sink inside their group and fall to Other below
  `SORT_FIT_THRESHOLD` (500). Rank scores at or above `SORT_MATCH_THRESHOLD` (600) are
  "Matches". Requests pack ≤ 400 questions / ~40k estimated tokens, 8 run at a time, transient
  errors are retried once (honouring `retry-after`), a chunk is split on `max_tokens_exceeded`,
  and what couldn't be scored comes back in `retry`. The response is parallel integer arrays
  (`ids`, `s` 0..1000, and for groups `g` and `n` 0..1000). Model pinned (`SORT_MODEL`); any
  change to a question string, the levels or the parse bumps `SORT_RUBRIC` (client score mirrors
  are keyed by it) and should be re-measured first with `npm run eval:sort` (tune split, then
  holdout once). The key, prompt and group text are never logged.
- **Piggyback.** With an active custom sort, `/api/combine` carries `sort`; a result that is new
  for the player is scored alongside the challenge check (`scoreDiscovery`, capped at 800 ms,
  never fails the combine) and returned as `sortScore`, so a discovery usually costs no extra
  call. It charges `BUDGETS.jev` first and calls Jev only once that passes, with what is left of
  the 800 ms, so `JEV_DAILY_CAP` bounds piggyback spend too.
- **Client engine** (`src/app/state/customSort.ts`, pure helpers in `lib/customSort.ts` and the
  ordering in `lib/librarySort.ts`). `reconcile()` is the only scheduler: on owned/status/sort
  changes it starts one full run when little is known, or queues the missing ids for a batched
  `{ids}` request (2.5 s debounce, 8 s cap, at once at 100 ids; one in flight). Failures never
  clear the order on screen; rate limits and the budget wait out their `until` (with more than
  30 s left, queued ids sort as unscored rather than pulsing as pending until the last 30 s).
  Reverse, Other, the Matches/group buckets and pins are display options that never call the
  server. Scores are cached per spec (LRU of 4) and keyed by player; a player switch or library
  reset drops every cache and aborts everything in flight. A spec counts as cached only when its
  entry is complete (a whole-library run, or the session mirror of one): piggybacked or batched
  scores alone never skip the full run. Picking ✦ in the sort select for a spec that isn't
  cached waits 400 ms (and for as long as the sheet is open) before any request, so arrowing
  through a native select costs nothing; responses for an older generation, key or player are
  dropped on arrival.
- **Storage.** `ia:customSort` (localStorage, ~1 KB: spec, view, 5 recents, previous sort,
  seen) and `ia:customSortScores` (sessionStorage: the active spec's scores tagged with player,
  key and rubric, plus the owned ids the server ruled out and the truncated flag, so a reload in
  the same tab re-sorts with no request, even for a library over 25,000). Nothing in the DB.

## Analytics

Two sources, used together. Neither may ever affect gameplay (failures are swallowed/logged).
Pull the numbers with `npm run analytics:pull` (GA4, Search Console, Bing) and
`npm run analytics:snapshot` (DB aggregates); both write to the gitignored `.analytics/`.

- **Server (ground truth for retention; ad blockers can't hide it).** Migrations 0006 and 0007.
  - `player_days (player_id, day, loads, combines)`: one row per player per **local** calendar day
    with activity (the validated client date, as daily challenges use; rows before 2026-11-09 are
    UTC-dated). Bootstrap counts a load (`touchPlayer`), each server-answered combine counts a
    combine (`countActivity`). Cohort day = a player's first `player_days.day`; D1/D7 = activity on
    that day + 1 / + 7.
  - `player_days` timing (migration 0009), in the same upsert (`activitySql`, no extra round
    trip): `first_at` / `last_at` = first and latest counted event; `sessions` = 1 + pauses over
    30 minutes; `active_secs` = sum of gaps of at most 5 minutes; `entry` = how the day's first
    bootstrap that sent one was reached (`search` | `direct` | `standalone` | `other`, classified
    client-side from `document.referrer` at page load, never the URL; NULL on a day that began with
    a combine from a tab left open; a resumed-tab refresh counts nothing). Combines the client answers from
    its recipe cache never reach the server, so `active_secs` runs slightly low. Rows begun before
    0009 have no `first_at` and are skipped by timing analyses.
  - Bootstrap `hint` (`BootstrapHint`; each malformed field dropped, never a 400): `touch`
    (`maxTouchPoints > 1`), `wide`, `prior` (a v2 game key such as the canvas or recipe cache was in
    localStorage before this load; never `ia:acq`, which the page head writes on every first

    `players.acq_touch` (with `acq_ua_class = 'mac'` it marks an iPad; `acq_ua_class` itself is
    unchanged), `acq_wide`, `acq_prior_local` (a "new" player in a browser that already had game
    state lost its cookie). Any bootstrap with `standalone` stamps `players.standalone_at` once,
    in the `last_seen_at` update the load writes anyway. Every writer falls back to its pre-0009

    signals, never loads, players or combines.
  - `players.acq_*`: first-touch referrer host, landing path and UTM tags, written once at player

    links carry `utm_source=share&utm_medium=social&utm_campaign=share_<surface>` (`shareUrl`).

  - Already there: `discoveries.discovered_at` (new elements), `challenge_completions`, `elements.discovered_by`.

  `src/app/lib/analytics.ts`). `user_id` = `players.public_id` (random UUID) and user properties
  `legacy_player` and the experiment arms (`exp_first_run`, `exp_idle_card`, `exp_goals`, set
  right after bootstrap), so a GA export joins to the DB. Params are only queryable in GA reports/API
  once registered as custom dimensions/metrics (not retroactive: register on ship day).
  `track()` drops GA4-reserved param names (`source`, `medium`, `campaign`, `page_*`, `user_id`,

  sessions. Key events: `first_combine`, `challenge_complete`.
  Event semantics (count with these in mind):
  - `app_ready`: bootstrap succeeded and the game is playable. `pow` = this load created the
    player (brand-new), `boot_ms` = navigation start to playable (retries and error-screen time
    included), `boot_band` = it bucketed (`<2s`, `2-4s`, `4-8s`, `8-15s`, `15-30s`, `30s+`: the
    server's boot stat bands), `pow_ms` / `api_ms` = this attempt's PoW solve and bootstrap
    round trips, `attempt` = bootstrap attempts
    this page load (2 is normally the automatic retry), `manual` = started from the error
    screen's Try again, `elements` = library size, `wide` = the right panel (challenge card) is
    on screen, `standalone` = installed app.
  - `load_failed`: the boot ended on the error screen (after the automatic retry, if it got one).
    `code` (ApiFailure code, or `network`), `phase` (where it failed: bootstrap1 | pow |
    bootstrap2 | render), `status` (HTTP status, 0 = no response), `attempt`, `manual`, `visible`
    (boolean: the tab was on screen; a reload or tab close aborts the fetch, which also reads as
    `network`), `online` (boolean, `navigator.onLine`). Retry rate = `load_failed` ÷ (`app_ready` +
    `load_failed`); retry success = `app_ready` with `attempt` 2 and `manual` false.
  - `boot_abandon`: hidden or left before ready, once per page: `phase` (as the beacon) and
    `boot_ms` (navigation start until then, as `app_ready`'s). GA only sees it when gtag had
    loaded, and it is never taken back: dedupe against `app_ready` per user. The `boot_abandon:*`
    and `boot_resumed:*` stats count every one.
  - `report`: "Report this element" sent, `reason` (inappropriate | wrong | other) and `outcome`
    (sent | limited | failed).
  - `onboarding`: the first-run welcome. Control (the modal sheet): `action` = shown | start
    ("Start mixing") | dismiss (Esc, backdrop, ×) | link (`target`), with `secs` open (capped at
    600). firstRun treatment (the collapsed welcome card): shown | expand | start | dismiss | link,
    `secs` since shown.
  - `coach` (firstRun treatment): the pill on the seeded demo pair. `action` = shown | done (the
    first combine; `demo` = it used the seeded pair) | dismiss (`via` = close | removed: the pair
    left the board first), `mode` = drag (fine pointer) | tap, `secs` since shown.
  - `milestone`: the library reached a goal rung, `rung` = 25 | 50 | 100 | 150 | 250 | 500. Sent in
    both goals arms (only treatment shows the toast), so GA compares how many reach each rung.
  - `celebration`: a world-first's reward, `kind` = card | toast, `reason` = session_first |
    notable | rare (the full card, always) | random_card | random_toast (the 50/50 draw), `rarity`.
  - `wf_followup`: one per world-first, when it settles: `kind`, `reason`, `cont60` (boolean: a
    combine started within 60 s) and `via` = combine | timer (60 s passed) | hidden (page hidden
    first). Compare only `random_card` against `random_toast`.
  - `idle_card` (idleCard treatment): `action` = shown, with `via` = idle | active (what triggered
    it), `discoveries` and `firsts` (today's, as shown), `offer` = install | tip | none, `teaser` =
    art | blank | none; then dismiss | home ("Play at home") | install, with `secs` since shown.
  - `install_eligible`: the browser fired `beforeinstallprompt`, once per tab session, sent after
    `identify()`: `prevented` (boolean: the browser's prompt was held back for the card) and `arm`
    (the player's real idleCard arm; it can differ from `prevented` when the event beat bootstrap).
  - `install_prompt`: our prompt was shown, `outcome` = accepted | dismissed | failed.
  - `install`: `appinstalled`, `via` = prompt (ours) | browser (the browser's own UI).
  - `first_tile`: the first tile placed this tab session, `via` = tap | drag.
  - `sheet_open`: a sheet opened, `sheet` = challenges | stats | settings | about | customSort.
  - `combine`: a **successful** combine, once per result. `cached` = answered from the client's
    recipe cache (no request), `new` = new for this player. A failed attempt is `combine_failed`
    (`code` = ApiFailure code or `network`; `limit` = the server rule that refused, e.g.
    `llm.player`, or `platform` for a bare 429; `retry_s` = the retry hint bucketed `<5` | `5-30` |
    `30-120` | `120+`) instead, so attempts = `combine` + `combine_failed`.
  - `first_combine`: the first successful combine **per browser-tab session** (sessionStorage),
    i.e. an activated session, not once per player. Player activation = new users (or
    `app_ready.pow`) who reach it.
  - `discovery`: a combine whose result is new for this player (`first` = also a world-first).
    `first_discovery` = a **world-first** (no player made this element before), not the player's
    first discovery; it fires alongside `discovery` with `first: true`.
  - `challenge_complete`: once per player per day per tier (`tier` = easy/hard/expert; the server
    dedupes on `challenge_completions`). One player finishing all three tiers = 3 events.
  - `share`: `surface` (details/celebration), `outcome` (shared/downloaded/cancelled/failed), `first`.
  - `custom_sort`: see "Custom sort" (`from` = where the sort was picked: typed, example, …).
  - `challenge_complete_easy|hard|expert`, `element_combined` and `element_cleared` come from the
    2023 app (replaced 2026-11-06), not this code; they only appear in history.
- **Feed.** The "fresh from the lab" feed (`recentElements`) lists the 20 newest active elements
  whose art is ready, not the raw newest (which almost never had art yet), from the partial
  covering index `elements_fresh_idx` (migration 0009; without it, a full scan of `elements`).
